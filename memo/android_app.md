# PDR計測アプリ(Android, MainActivity.kt)

このリポジトリの外(Android Studioプロジェクト、別のClaude Codeセッションで開発)に
あるPDR計測アプリの変更・レビュー記録。CSV出力を実際に読むのは`pdr_pf_improved.py`
側(このリポジトリ)なので、フォーマット変更はここに記録する。

### 2026-09-03: Sonnet 5版のレビューと堅牢化(プロジェクトの場所も判明)

- **プロジェクトの場所**: `~/AndroidStudioProjects/test2`(パッケージ`com.example.test2`、
  実体は`app/src/main/java/com/example/test2/MainActivity.kt`の1ファイル)。
  単独のgitリポジトリではないためdiffが取れない。差分が必要なときは
  `~/.claude/projects/-Users-soma-AndroidStudioProjects-test2/*.jsonl`のセッションログから
  修正前のファイル内容を復元できる(今回はそうして新旧を比較した)。
- 経緯: Sonnet 5が書いた版をOpus 5でレビュー・修正し、さらに解析側セッション(こちら)で
  コードを読んで再確認した。こちらが指摘した3点も追加で修正されている。
- **CSV出力フォーマットは不変**。ヘッダ・1行の連結式・`event.timestamp / 1e9`とも旧版と
  完全一致することを確認済みで、過去データとの後方互換性は保たれている。

修正内容(重要な順):

1. **画面回転で記録が黙って止まる**。manifestに`screenOrientation`も`configChanges`も無く、
   記録中に端末が回るとActivityが再生成され`onDestroy`でセンサー解除・ファイルクローズが
   走っていた。画面は「停止中」に戻るので歩き続けても途中までしか残らない。
   `portrait`固定＋`configChanges`を追加。
2. **同一分内の再記録で先のCSVを上書き**。ファイル名が`pdr_log_MMdd_HHmm`で`FileWriter`は
   追記なし。衝突時のみ`_2`, `_3`を付けるようにした(通常時の名前は従来通り)。実測が
   1441/1442と1分刻みで1回の歩行が45〜67秒だったことを考えると現実的なリスクだった。
3. **地点マークCSVの時刻がメインCSVと別時計になりうる**。メインは`event.timestamp`、
   地点マークは`SystemClock.elapsedRealtimeNanos()`基準。両者の差の観測最小値で補正する
   ようにしたが、**採取元は`TYPE_LINEAR_ACCELERATION`のイベントに限定すること**。
   メインCSVを書くのはこのセンサーだけなので、他センサーを混ぜると時計基準の違う端末で
   別センサーのオフセットがminを奪い、かえってメインCSVとずれる(初版は全センサーから
   採取していた。指摘して修正済み)。なお時計基準そのものは2026-08-16に実機で一致を
   確認済み(下の「2026-08-16(追記)」の項)なので、この補正は基準が異なる端末に備えた
   防御であり、一致する端末ではオフセットはほぼ0で従来と同値になる。
4. **`x, y`列の符号**を`(cos, sin)`→`(sin, cos)`に変更。Androidのazimuthは北=0・東=+π/2
   (−z軸まわりの回転)なので、x=東 / y=北 の座標系では進行方向の単位ベクトルは`(sin, cos)`。
   旧式は反時計回り前提で軌跡が左右反転していた。**解析側はこの列を読んでいない**ことを
   確認済み(`validate_log`の必須列は`timestamp, acc_*, gyro_*`のみ、`df['x']`の参照なし)
   なので研究結果への影響はない。ただし`pdr_log_0805_*`など2026-09-03以前のCSVの`x, y`は
   旧(反転)規約なので、新旧を混ぜて比較しないこと。
5. **STOP時の自己診断を追加**。記録時間・行数・平均サンプリングHz・ウェイポイント数を
   表示し、(a)1行も記録されていない (b)記録中にバックグラウンドへ移行した
   (c)0.5秒を超えるギャップがある のいずれかがあれば`setCancelable(false)`のダイアログで
   ブロックする。**取り直しの効かない実測データなので、研究室に戻ってからではなく
   現場で欠落に気づけることが目的**。末尾で切れた場合はギャップとして出ないが、
   その場合も「記録時間」を実際の歩行時間と突き合わせれば気づける。
6. **書き込みの間引き**。1行ごとflush→200msごと＋地点マーク押下時＋`onPause`時＋STOP時。
   UI更新は10Hzに間引き、`event.values.clone()`→`System.arraycopy`。既存3CSVのdtは
   0.0189sで完全に均一(落ちゼロ)なので53Hzでは実害は出ていなかったが、
   `HIGH_SAMPLING_RATE_SENSORS`を宣言している以上サンプリングを上げると効く。
7. **失敗の可視化**。ファイル作成に失敗しても「記録中」表示になっていたのを、失敗時は
   開始しないようにした。線形加速度センサーが無い端末ではCSVが1行も出ないため、
   必要センサーの欠落を起動時に警告する。
8. `ACTIVITY_RECOGNITION`の実行時許可リクエスト(Android 10以降、歩数系センサーに必要)。

未解決・未確認:

- **バックグラウンド遷移でセンサーが止まる問題は未解決**。Android 9(API 28)以降、
  フォアグラウンドサービスを持たないアプリがバックグラウンドへ回ると、連続報告センサーも
  STEP_DETECTORもイベント配信が止まる。上記5で検知は入ったが根本解決ではない
  (根本解決には常駐通知＋`FOREGROUND_SERVICE`権限＋`foregroundServiceType`指定が要る)。
  当座は**計測中に機内モードにして着信という最大のトリガーを潰す**運用にする。
- 地点マークCSVの時刻基準そのものは**2026-08-16に実機確認済みで問題なかった**
  (下の追記の項)。未了なのは「補正コードを載せた版」での確認で、次の計測時に
  waypointsのtimestampが本体CSVの時刻範囲に収まっているかを最初に見ておくこと
  (補正が余計なズレを生んでいないかの確認)。
- 2026-08-16に未確認だった**日本語の文字化けは解消を確認**。ファイルは正常なUTF-8で
  `"■ 停止中"`等が正しく格納されている。当時は貼り付け経路上の表示問題だった可能性が高い。

関連: 派生CSV(`pdr_log_*_waypoints.csv`)を解析側のglobがセンサーログとして拾ってしまう
問題は同日に修正済み(CHANGELOG.md 2026-09-03(0)項、`is_sensor_log_csv()`)。

### 2026-08-16: CSVフォーマット拡張(mag_x/y/z・waypoints・memo)のレビュー

- **背景**: サンプル数不足([route_source_auto.md](route_source_auto.md)のL字マップの
  項目、及び8.7節「提案方式の限界」で挙がっていた「正解位置データが無い」「磁気センサ
  が無い」という2つの限界)への対応として、Android側のPDR計測アプリ自体に機能追加が
  必要と判断。Android Studio側で動く別のClaude Codeセッションに指示を出す前提で、
  このセッション側から要件をまとめたプロンプトと、Android側の`CLAUDE.md`叩き台を
  作成しユーザーに渡した。
- **依頼した変更**(優先度順):
  1. **正解位置(グラウンドトゥルース)記録機能**: 記録中に「地点マーク」ボタンを押すと、
     押した瞬間のタイムスタンプと連番を、メインCSVとは別の`_waypoints.csv`
     (列: `timestamp, seq`)に追記する。8.8節「今後の課題」の(4)区間ごとの正解位置
     データ作成に直結する最優先項目。
  2. **地磁気センサ(mag_x/y/z)の追加記録**: 既存列の末尾に追加。8.7節の限界
     (磁気センサが無く方位が磁北補正されない)への対応。
  3. (余裕があれば)記録セッションのメモ機能(自由記述、`_memo.txt`として保存)。
  4. 制約として、既存CSV列(`timestamp, acc_x/y/z, gyro_x/y/z, yaw_deg, x, y`)の削除・
     リネーム・順序変更は禁止(過去の実測データとの後方互換性のため)と明記した。
- **実装結果の確認(1回目のコードレビュー)**: 依頼通りmag_x/y/z追加・waypoints CSV分離・
  memo.txt機能は実装されていたが、以下の問題を発見:
  1. 日本語文字列が全て文字化け(典型的なUTF-8→Latin-1系のmojibake)。ボタンラベル・
     Toast・AlertDialogの表示文字列に影響。
  2. `TYPE_ACCELEROMETER`ハンドラ内で`lastStepTime`、`TYPE_LINEAR_ACCELERATION`
     ハンドラ内で`linearAccData`という、クラスプロパティとして宣言されていない変数を
     参照しており、コンパイルが通らない可能性が高いと指摘。
  3. `posX`/`posY`(画面表示用のリアルタイム位置)が、`TYPE_ACCELEROMETER`の自作閾値
     判定(振幅>11.0かつ400ms以上経過)と`TYPE_STEP_DETECTOR`(Android標準の歩数検出)
     の両方で更新されており、二重カウントの懸念を指摘(ただし`pdr_pf_improved.py`側は
     CSVのx,y列を評価に使わず、acc/gyro生値から独自にSmartPDR歩幅推定をやり直すため、
     実害は画面表示の不正確さのみと判断)。
  4. `_waypoints.csv`のタイムスタンプが`SystemClock.elapsedRealtimeNanos()`基準、
     メインCSVは`event.timestamp`(Androidのセンサーイベントタイムスタンプ)基準で、
     両者が同じ時計基準である保証は機種・OSバージョンによって崩れうる(既知の
     Android仕様上の落とし穴)ため、実機で「STARTした瞬間に地点マークを押し、
     waypoints.csvの1行目と本体CSVの先頭行のtimestampが近い値になっているか」を
     確認するようユーザーに依頼した。
- **2回目のコードレビュー(修正後)**:
  - ②(未宣言変数)は解消。`TYPE_ACCELEROMETER`ハンドラの自作歩数検出ロジックが
    まるごと削除され、`accData`をキャッシュするだけになった。これにより③(二重
    カウント)も同時に解消(posX/posYの更新が`TYPE_STEP_DETECTOR`ハンドラの1箇所
    のみになった)。
  - 副次的な改善として、Android 10以降で歩数系センサーに必要な`ACTIVITY_RECOGNITION`
    実行時許可のリクエストが追加されていた(依頼していなかったが、こちらから
    指摘していなかった潜在バグの先回り対応)。`onDestroy()`でログ中に強制終了された
    場合もファイルをflush/closeするようになった(同様に自主的な堅牢化)。
  - ①(文字化け)は貼り付けられたコードでは依然として同じパターンで見えたが、
    これがファイル自体の保存エンコーディングの問題か、Android側Claude Codeの出力
    →この会話への貼り付け経路上の表示だけの問題かはこちらからは判別できないため、
    Android Studioのエディタで直接開いて日本語が正しく表示されるか確認するよう
    依頼(**未確認のまま**)。
  - ④(waypointsのタイムスタンプ基準の実機確認)も**未確認のまま**。

### 2026-08-16(追記): ④実機確認 完了・問題なし

- `pdr_log_0816_1015.csv`(本体, 先頭455.893988751〜末尾461.362620886)と
  `pdr_log_0816_1015_waypoints.csv`(seq=1, timestamp=457.231436647)を実機で取得し比較。
  waypointのtimestampが本体CSVの記録区間内にきれいに収まっており、両者が同一の
  時計基準(起動からの経過時間)で動作していることを確認。もし基準がズレていれば
  桁違いの値(例: epoch秒なら17億台)になるはずだが、そうなっていない。
  差分(457.231 - 455.894 ≈ 1.34秒)はSTART押下後に地点マークボタンを押すまでの
  操作の遅れとして妥当な範囲。
  ※1回目の試行(`pdr_log_0816_1011`)ではボタンが画面下すぎて押せず
  waypoints.csvが空だったため、地点マークボタンをcontrolRow(START/STOP)の直下・
  画面中央付近に移動する修正をAndroid側Claude Codeセッションに実施(色・サイズは変更なし)。
  修正後の2回目の試行で上記の確認が取れた。
- **結論**: タイムスタンプ基準の統一対応は不要と判断。実機確認が取れたので、
