## 2026-09-03: Phase 0(目印の座標表)を設計した

### 結論として採った方式

**マスター表 + 経路定義** 方式。物理的な目印を1つの表(`ground_truth/
kanri_4f_landmarks_master.csv`)に持ち、`routes.json` で「この順に押す」という
IDの並びを与えて、経路別のlandmarks CSVを `make_route_landmarks.py` で生成する。

経路ごとに別ファイルが要るのは、`build_ground_truth.py` が waypoints と landmarks の
**seqの集合の完全一致**を要求するため。逆方向に歩く経路は、同じ物理点をIDの並びだけ
逆にすれば seq が振り直される。手作業で経路の数だけCSVを作ると押す順番とseqがずれる
事故が起きるので、生成に寄せた。

### pick_landmarks.py は使わない(重要)

`pick_landmarks.py` はPFが使う二値地図を表示してクリックさせる設計だが、
**kanri_4fの二値地図は廊下沿いに開口が1つも無い**。下側廊下の北壁・南壁を
x=88〜390まで2px刻みで走査しても壁が連続しており、上側廊下も同様だった。
つまり真っ白な帯のどこをクリックすべきか判断できず、クリックの精度が出ない。

座標は、元の平面図から検出した壁位置(整数px)と現地でのメジャー実測から決める方が
正確である。**このプロジェクトでは pick_landmarks.py を使わない**。
ファイルは参照用に残す。

### 平面図が二値地図と同一の座標系で使える(発見)

`map_binarizer.py` は切り抜き(--crop)しかせず拡大縮小をしない。そのため
`kanri_4f_preview_final3.png` の1枚目のパネル(cropped original)は、二値地図と
**1px単位で一致する**。実際に3枚目のパネルと `kanri_4f_binary_final3.png` が
`np.array_equal` で完全一致することを確認した。

これを切り出した `ground_truth/00_平面図_地図と同一座標系.png` を使えば、
部屋名・壁位置を見ながら地図座標を直接決められる。**今後、地図上の位置を
議論するときは常にこれを使うこと**(二値地図だけを見て議論しない)。

### 平面図にドアは1つも描かれていない(確認済み)

廊下に面した4本の壁すべて(下側廊下の北壁・南壁、上側廊下の北壁・南壁)について、
壁線の帯の最暗値を走査したところ**開口が1つも無かった**。二値化の副作用ではなく、
二値化前の原図の時点で描かれていない。簡略化された平面図である。

→ **ドアを目印にする場合、座標は現地で実測するしかない。**

### 通り芯(柱)は使わないことにした

平面図には x = 76 + 51.7k (k=0..17) の等間隔な丸印が建物全体を貫いて並んでおり、
51.7px = 4.54 m。目印として理想的な密度と均一性だったが、**ユーザーが「廊下を
歩きながら±0.5 m以内で判断できるのは、研究室の入口ドアと部屋の境界の壁」と
回答したため採用しなかった**(柱型が廊下に出ているかは未確認)。

ただし縮尺の検証には間接的に使える(下記B)。現地で柱が識別できると分かれば、
均一な目印として再検討する価値がある。

### 曲がり角そのものは目印にしない

ホール233は幅4.3 mの開けた空間で、「折り返した点」に物理的な目印が無い。
代わりに、両側の壁が同時に途切れる **L05(386,230) 廊下→ホール** と、
左右の壁の切れ目の間を通る **L06(412,131) ホール→上側廊下** を使う。
どちらも門をくぐる形なので通過の瞬間が明確。

### 目印の質の序列(現地で使える目安)

1. **南北両側で同時に境界が来る点** — x=231 / 386 / 489 / 696。最も分かりやすい
2. 片側だけの室境界の壁 — x=128 / 748 / 852 / 903
3. 廊下の端の外壁 — x=26(西) / 955(東)。背をつけて立てるので始点終点に最適
4. ドア — 現地では明確だが図面に無いので実測が要る

### 縮尺の検証(レーザー距離計が借りられないための設計)

`scale_px_per_m = 11.4` は実測で裏を取っていない。5mメジャーしか無いので、
31.6 mを継ぎ足しで測る案は誤差が積み上がるため捨てた。代わりに
**同じ側の壁どうしで、メジャー1本で測り切れる約4.5 mの4区間**(合計206px)を測り、
`206 ÷ 実測合計` で縮尺を出す。独立した4回の平均になるので精度も上がり、
実測値どうしの比が図面の比と合うかで**平面図自体の歪み**も検出できる。

**落とし穴**: 図面のx座標は壁の**中心線**。部屋の内寸(壁の面から面まで)を測ると
壁厚1枚分(約0.2 m)短くなり、4.5 mの区間では4%ずれて縮尺検証としては致命的。
**同じ向きの面どうし**(西面→次の壁の西面)で測れば壁厚が相殺される。
ドアの採寸ではこの0.2 mは位置誤差0.2 m相当にしかならず、RMSEがメートル単位である
以上ほぼ影響しない — 神経質になるのは縮尺検証だけでよい。

### 経路の設計

始点は西の外壁(x=26)に背をつけた位置。終点は東端の壁(x=955)の手前。
**両端とも壁なので立ち位置が毎回再現できる**。ユーザーの希望した x=800 / x=200 は
どちらも目印の無い位置だったため、近い室境界に寄せた(x=748 / x=231)。

定義した経路は rehearsal(図面確定分のみ13点、現地採寸を待たずに使える) /
east_std(14点) / east_short(12点) / west_reverse(12点、逆方向) / east_dense(18点)。
east_std・east_short・west_reverse は最大間隔11.4 m・平均約6.7 mに揃えてある。

### 計測当日の健全性判定(`quick_check.py`、2026-09-03追加)

計測日に学校にいるうちに撮り直しの要否を決めるための読み取り専用ツール。
アプリのSTOP時ダイアログが既に出す項目(記録時間・行数・Hz・欠落・バックグラウンド
遷移)は**重複させず**、計算しないと分からない項目だけを見る:
歩数・歩調・平均歩幅・推定総移動距離 / 方位の正味回転・振れ幅・最大ジャンプ /
地点マークのseqと時刻整合 / START直後の静止。

歩数と歩幅は `pdr_pf_improved.py` の関数をimportして計算する(自前で計算し直すと
本体とずれた数字を見て「問題なし」と誤判定するため)。`load_map_config_for_tool()` を
先に呼ばないと `M_TO_PIXEL`・`STEP_LENGTH_CALIBRATION_GAIN` が設定されず、
本体と違う定数で計算した数字が出る点に注意。

**距離判定を2段階にした理由(非自明)**: 当初 想定距離からのずれ±15%超を「異常」に
したところ、手元の実データ7本が全て異常になった。原因は歩幅校正ゲインが暫定値(2.10、
評価用と同じ3CSVから求めたもの)で、実測が想定より2割ほど短く出ることが既知
(CLAUDE.md「歩幅校正の残差(約20%の過小)」)だったため。計測当日に全記録が異常判定に
なると本当の問題を見落とすので、±15%超は「警告」、±40%超を「異常」とした。
**歩幅モデルを再同定(§27.2 C)したら `DISTANCE_BAD` を締めること。**

実データでの検証: `pdr_log_0805_1438.csv` を方位の正味回転(-32度 / 想定-90度)で
初回チェックで異常判定できた。このファイルは過去に真因の特定まで2週間かかったもの。
`1442` の最大ジャンプ151.3度も memo/sensor_mystery.md の記録と一致した。
